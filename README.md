## Як запустити

1. Відкрити `BankingWebTests.sln` у Visual Studio 2022.
2. Дочекатись, поки NuGet відновить пакети (або `Build → Rebuild Solution`).
3. `Test → Test Explorer` → **Run All Tests**.

З командного рядка:

```bash
dotnet test
```

Запустити лише коректні сценарії або лише сценарії з дефектами:

```bash
dotnet test --filter "TestCategory=positive"
dotnet test --filter "TestCategory=defect"
```

Прогін без вікна браузера (для сервера збірки):

```bash
BANK_HEADLESS=true dotnet test
```

```
│   ├── BasePage.cs                   спільне: драйвер і явні очікування
│   ├── HomePage.cs                   стартова сторінка
│   ├── CustomerLoginPage.cs          вибір клієнта і вхід
│   └── AccountPage.cs                рахунок + форма Withdraw
├── Support/
│   ├── TestSettings.cs            налаштування в одному місці
│   ├── DriverFactory.cs           створення браузера
│   ├── BrowserHooks.cs            відкриття/закриття браузера, знімки екрана
│   └── ConsoleErrorCollector.cs   перехоплення помилок JavaScript
└── reqnroll.json                  конфігурація Reqnroll
```

**Головне правило Page Object Pattern** дотримане строго: жодного локатора
поза текою `Pages/`. Крок тесту каже «увійти як Hermoine Granger», а не
«знайти елемент `#userSelect`». Якщо сайт змінить розмітку, правити треба
буде один клас сторінки, а не двадцять сценаріїв.

## Чому тестові дані детерміновані

XYZ Bank — це застосунок на AngularJS без сервера: усі дані він тримає
у `localStorage` браузера. Якщо сховище порожнє, при завантаженні
виконується `mockDataLoadService.js`, який створює:

* 5 клієнтів (Hermoine Granger, Harry Potter, Ron Weasly, Albus Dumbledore,
  Neville Longbottom), кожному по 3 рахунки — Dollar, Pound, Rupee;
* операції **тільки для першого клієнта на першому рахунку**:
  7 місяців × 28 днів, щодня «+30 і −4».

Звідси початковий баланс рахунку **1001** клієнтки Hermoine Granger:

```
7 × 28 × (30 − 4) = 196 × 26 = 5096
```

Решта рахунків порожні.

Крок `Given the application state is reset` очищає `localStorage`
і перезавантажує сторінку, тож **кожен сценарій стартує з балансу 5096**.
Саме тому у сценаріях можна писати конкретні очікувані суми, а не
«баланс зменшився приблизно на стільки ж»: це не здогадка, а точне число.

## Знайдені дефекти

### Як писався кожен тест

Усі сценарії проєкту написані за одним правилом: **очікуваний результат
береться з вимоги, а не з фактичної поведінки застосунку**. Якби очікування
виводили із самого сайту («запустив, побачив, записав»), тест міг би
підтверджувати лише те, що програма робить те, що робить, — і не виявив би
жодного дефекту.

Письмової специфікації у XYZ Bank немає: це демонстраційний сайт. Тому
джерелом вимоги є, у порядку пріоритету:

1. **те, що застосунок сам про себе заявляє** — тексти повідомлень, які він
   визначає, і підписи на формі;
2. **поведінка застосунку в аналогічному випадку** — якщо для суми 100 він
   відповідає повідомленням, то для суми 0 мовчати він не має права;
3. **загальні вимоги до банківської операції** — клієнт мусить отримати
   відповідь на кожен запит, сума зняття має бути коректною.

Джерело вказане окремо для кожного сценарію у коментарях `.feature`-файлів.

### Чому частина тестів червона

Сценарії з тегом `@defect` падають не тому, що підібрані під падіння. Вони
написані так само, як решта, і з того самого джерела вимог — і падають тому,
що застосунок цих вимог не виконує.

Тести **не поділені** на «зелені» і «червоні» файли. Групування за наслідком
було б помилкою: результат стає відомий лише після запуску, а коли дефект
виправлять, тест довелось би переносити в інший файл. Сценарії згруповані за
предметом перевірки — зняття в межах балансу, межі, некоректна сума, стан
форми, — а тег `@defect` лише позначає поточний статус.

Це і є визначення збою з Лекції 1, п. 5.1: *«Збій (Failure) – це відхилення
фактичного результату роботи від очікуваного, яке спостерігається при
виконанні програми»*. Червоний тест — це зафіксований збій, а не зіпсований
тест.

Корінь дефектів Д1–Д4 знайдено у вихідному коді самого сайту.

`transaction.service.js`:

```js
function transaction(user, account, depAmt, wdAmt, date) {
    var txObj;                                   // ← оголошено, але не створено
    if (depAmt && depAmt > 0) { txObj = {...} }
    if (wdAmt  && wdAmt  > 0) { txObj = {...} }
    return txObj;                                // ← для 0 і від'ємних → undefined
}
```

`withdrawlController.js`, рядок 10:

```js
var txObj = Transaction.withdrawl(...);
if (!txObj.success) { ... }                      // ← TypeError, якщо txObj === undefined
```

| № | Дефект | Прояв |
|---|---|---|
| Д1 | Зняття суми **0** не дає жодного повідомлення | клієнт не знає, виконано операцію чи ні |
| Д2 | Після зняття 0 поле суми **не очищається** | обробник обірвався, не дійшовши до `$scope.amount = ""` |
| Д3 | У консолі браузера — необроблений **TypeError** | `Cannot read properties of undefined (reading 'success')` |
| Д4 | **Від'ємна** сума обробляється так само мовчки | немає валідації знака |
| Д5 | Сума, **менша за найменшу одиницю валюти**, приймається | рахунок ведеться в доларах, найменша одиниця — цент; 0.001 проходить, баланс стає 5095.999 |
| Д6 | Повідомлення про помилку **не зникає** при зміні рахунку | текст про помилку на рахунку 1001 висить над рахунком 1002 |

Дефект Д3 винесений в окремий файл `WithdrawReliability.feature` з тегом `@reliability`: він перевіряє не функціональну вимогу, а показник надійності. Його неможливо побачити ні на знімку екрана, ні в тексті сторінки:
AngularJS перехоплює виняток своїм `$exceptionHandler` і лише пише його
у консоль. Тому `ConsoleErrorCollector` перед сценарієм підміняє
`console.error` власною обгорткою, яка додатково складає всі повідомлення
у масив — і тест може їх перевірити.

## Точні тексти повідомлень застосунку

Зняті з вихідного коду `withdrawlController.js` / `depositController.js`
і перевірені на живому сайті — тести звіряють їх посимвольно:

| Подія | Текст |
|---|---|
| Успішне зняття | `Transaction successful` |
| Сума більша за баланс | `Transaction Failed. You can not withdraw amount more than the balance.` |
| Успішне поповнення | `Deposit Successful` |
